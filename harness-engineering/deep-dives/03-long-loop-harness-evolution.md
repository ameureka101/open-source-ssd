# 生产级全栈工程「Loop」使用全景总结

> 基于 2026-08-28 对 8 个专项的并行取证（workflow 9 agent / 磁盘直读核验）。
> 本文件回答三个问题：**loop 在项目里到底是什么**、**它怎么一路演进的**、**有哪些可复用的共性规律与教训**。

---

## 一、全景：8 个专项的 loop 使用一览

loop 不是某个单一文件，而是「**goal（意图）→ 契约（判据）→ 循环执行 → 报告（回填）**」的完整执行方法论。8 个专项全部落在这条轴上，但**强度、形态、复杂度随工作性质与时间演进而分化**。

| # | 专项 | 时间 | 命名风格 | 需求编号 | 技术域 | loop 形态 |
|---|------|------|---------|---------|--------|----------|
| 1 | 00-001 各阶段 bug 及优化 | 07-14 | `LOOP-执行契约` | 200 系 | 10 域 | 单契约，goal **内联**，25 specs 分 5 波 |
| 2 | 01 优化课程开始 | 07-08~11 | `impl-wN-execution-contract` + `impl-wN-goal.txt` | 编号式 | — | 顶层总纲 + **_loop 目录 5 wave 三件套** |
| 3 | 011 bug 修复记录 | 07-16(+07-23 二期) | `EXECUTION-CONTRACT-日期` | 300 系 | 8 域 | **单契约无 wave**，一期→二期追加 |
| 4 | 012 邀请链接机制 | 07-17~23 | `EXECUTION-CONTRACT-wave0/1/2` | 500/600/700 系 | — | **wave 嵌套子项目**，最复杂 |
| 5 | 013 上线后 bug 记录 | 07-22~23 | `EXECUTION-CONTRACT-wave-a~e` | 800 系 | 10 域 | 5 契约 + **6 报告**(wave-f 收口) |

## 二、演进脉络：五个维度的连续变化

### 2.1 命名风格（三阶段 → 五变体）

| 阶段 | 风格 | 代表专项 | 说明 |
|------|------|---------|------|
| 起点 | `LOOP-执行契约-日期` | 00-001 | 最早，中文，强调「loop」本体 |
| 一 | `impl-wN-execution-contract` + `impl-wN-goal.txt` | 01 | 引入 wave 编号 wN，goal 独立成 .txt |
| 二 | `EXEC-CONTRACT-batchN` | 03 | batch 缩写，另一条命名支线 |
| 三 | `EXECUTION-CONTRACT-wave-X-日期` | 013 / 011 | 契约与报告分离，wave 用字母(a~e)或日期 |
| 终点 | `GOAL-waveX-需求编号` + `EXECUTION-CONTRACT-waveX-需求编号-日期` | 06 | **goal 与契约分离 + 需求编号内嵌** |

**第五维度发现**：goal 从「内联于契约正文」（00-001 契约首行自述"本文件是 /goal 引用的执行契约"）演进到「独立 GOAL 文件」（06 的 `GOAL-wave1-ops901`）。这是命名演进之外的另一条主线。

### 2.2 需求编号体系：随时间严格递增

```
03 → 00-001 → 011 → 04 → 012 → 012 → 012 → 013 → 06
100    200     300   400   500   600   700   800   900
```
- 编号与专项创建时间单调递增，跨专项 +100 步进。
- **012 专项内部**还按 wave 递增（500→600→700），证明编号既是跨专项时间戳，也是专项内 wave 序号。
- 前缀约定灵活但结构稳定：`UI-`/`API-`/`INT-`/`SEC-`/`BL-`/`OPS-`/`QA-`/`DEP-`/`CODE-`/`NAV-`/`DB-` 覆盖 11 个技术域前缀；同一技术域在不同专项可用不同前缀（03 的 `NAV-101` vs 别处的 `CODE-`）。

### 2.3 技术域覆盖：随工作性质变化

- **功能/支付型专项最全**：03 有 10 域（含独有的 `30-database`）、013 有 10 域、00-001 有 10 域。
- **bug 修复型专项最简**：011 仅 8 域，是唯一不含 `60-security` 和 `70-code-standards` 的。
- **内容驱动型专项最少**：04 仅 3 域（10/40/70）。
- 技术域集合**随专项内容扩展**——`30-database` 只在支付专项出现，说明域不是固定模板，而是随需求长出。

### 2.4 契约与报告的体积关系（"报告回填"规律）

- **多数专项报告反超契约**：00-001(12479>11254B)、011(16872>8701B)、06 wave2(19356>8221B)、012 wave0(13600>11630B)。
- **唯一反例 03**：契约(10287B)>报告(8919B)，可能因报告写于次日未充分回填。
- **时序特征**：先契约→后执行→再报告，间隔从 8 小时（00-001）压缩到 2.5 小时（011）。
- **含义**：报告是"回填执行细节、验证结果、偏差说明"的载体，体积反超是真实执行的信号，而非纸面契约。

### 2.5 wave 分波的扩展性

- **单专项内 wave**：00-001 的 W1~W5、01 的 w1~w5、013 的 wave-a~f。
- **跨目录 wave 子项目**：012 把 wave0/wave1/wave2 各自独立成目录，每个都自含 requirements/requirements-specs/audit 子结构。
- **wave 命名对象演进**：wave 后缀从纯字母(a~e)、纯编号(wN)、到需求编号(ops901)混编。

## 三、共性规律：跨 8 专项不变的骨架

尽管形态多样，8 个专项共享一套**稳定内核**，这是 loop 方法论真正可移植的部分。

### 3.1 契约九块固定结构（最稳定、可跨语言移植）

以 00-001 中文契约（92 行）与 06 英文契约（68 行）为证，九块结构**完全同构**：

1. 目标与范围（Goal and Scope）
2. 队列真相源（Queue and Progress Truth）
3. 单件循环（Fixed Single-Item Loop）
4. 质量门（Quality and Completion Gates）
5. 决策政策（Decision Policy）
6. 中断恢复协议（Resume Protocol）
7. 停止条件（Stop Condition）
8. 非协商红线（Non-Negotiable Boundaries）
9. 终报（Final Report）

**语言可变（中/英），结构不变**——这是契约模式可移植性的最强证据。

### 3.2 以磁盘为队列真相源（不是对话记忆）

- 00-001 明确「**队列 = 磁盘状态，不是对话记忆**」，QUEUE_FILE 指向 `requirements/00-INDEX.md` 的 25 行表格。
- 06 的 Queue Truth 同样指向磁盘。
- **含义**：执行进度、verdict、回填都落盘，对话只是操作界面，磁盘才是真相。这让执行可中断、可恢复、可审计。

### 3.3 单件循环 + 硬质量门

- **单件循环步数**：00-001 为 6 步（前提复核→实施→对抗验证→质量评分→波内回归门→收口记录），06 为 7 步（新增「只 commit 明确 in-scope 文件」的 git 范围约束）。
- **质量门命令**：从 00-001 的 4 道（tsc/test/build/R_eff≥0.95）细化到 06 的 9 道（check:env / guard:attribution-secret / tsc / test:config / test:analytics / test:backend / test:seo / build / verify:ga4）。
- **R_eff≥0.95 硬门**：`R_eff = min(D1..D5)` 机械计算、禁手调，是跨专项的常驻质量红线。
- **verdict 五态收口**：Implemented / Spec-Premise-Stale / Deferred-Non-Blocking / Specs-Generated（非终态）等。

### 3.4 常驻红线（跨专项不变的硬约束）

- **DB 硬红线**：生产 Supabase 库不可迁移/不可执行 DDL（00-001、06 延续）。
- **git 边界**：只 commit、禁 push、禁切分支、禁触碰 main（00-001 禁 push；06 禁 `gh workflow run`）。
- **生产安全**：06 契约明确「默认验证不得发生产事件」「Never invoke gh workflow run」。

### 3.5 双目录中英双语命名

- `requirements/`：中文标题（如 `BL-301-二维码后台化管理能力.md`），便于人工阅读。
- `requirements-specs/`：英文 slug 子目录（如 `BL-301-qr-admin-management`），每个需求固定四件套（`01-requirements/02-design/03-tasks/04-fpf-review`），便于程序化索引。
- 两层通过**统一编号前缀**关联（`BL-301 ↔ BL-301`）。
- 这是「人机双友好命名」的通用经验。

### 3.6 审计收口 + 编号式需求结构

- 013 的 `audit-postlaunch-remediation`、012 的 `audit-referral-redemption-rewards`、00-001 的 `00-总览与决策台账`：**审计文档编号化**（00-09）是跨专项稳定模式。
- 需求文档普遍采用 00-08 编号式结构（01、06 shenji），形成「索引→需求→规格→审计」完整证据链。

## 四、经验教训：反例与边界

### 4.1 契约模式并非万能——04 是实证

04-营销 blog 是 **8 专项中唯一顶层无契约文件**的，顶层只有内容营销总纲 + blog 排期表，走「内容排期驱动」轻量路径，需求域最少（3 域）。

**结论**：loop 的强度应随工作性质调节——
- **代码/功能/支付型**（03、013）→ 重契约、多 wave、10 域。
- **bug 修复型**（011）→ 单契约、无 wave、8 域。
- **内容型**（04）→ 可完全走排期表，不必硬套三件套。

### 4.2 单契约无 wave 也是合法形态

011 用**单契约 + 二期追加**（07-16 一期契约，07-23 以 03/04/05 编号追加二期）而非新建 wave。证明 wave 分波不是必需的，追加式演进同样有效。

### 4.3 报告"反超契约"是常态、反例要警惕

03 是唯一契约>报告的专项，可能反映报告未充分回填。**建议**：报告应始终回填执行细节与验证证据，避免停留在纸面契约。

### 4.4 需求编号与技术域需随内容动态生长

- 编号严格递增是跨专项纪律（100→…→900），不应跳号或复用。
- 技术域不是固定模板（`30-database` 仅在支付专项出现），应随需求自然长出，而非预设全集。

## 五、可复用清单（给未来专项）

对任意新专项，可直接套用以下骨架：

```
[专项根目录]
├─ GOAL-waveX-需求编号-日期.md        ← 轻量意图（可选，从 06 起独立）
├─ EXECUTION-CONTRACT-waveX-需求编号-日期.md  ← 九块契约（核心判据）
├─ EXECUTION-REPORT-waveX-日期.md     ← 回填执行细节（体积应反超契约）
├─ requirements/                      ← 中文标题 + 00-INDEX（队列真相源）
├─ requirements-specs/               ← 英文 slug，每需求四件套
├─ 00-总览与决策台账.md               ← 编号化审计收口
└─ audit-*/                          ← 00-09 编号审计文档
```

**执行纪律**：
1. 契约九块结构不可省（语言可中可英）。
2. 队列真相源 = 磁盘表格，非对话记忆。
3. 单件循环 6~7 步 + 质量门命令 + R_eff≥0.95 硬门。
4. 常驻红线：生产库禁 DDL / git 只 commit 禁 push。
5. 需求编号单调递增，技术域随内容生长。
6. 内容型工作可走排期表轻量路径，不必硬套契约。
