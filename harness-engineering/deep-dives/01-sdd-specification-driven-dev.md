## 一句话结论

> **项目不是「先写代码再补文档」，而是一条从需求矩阵到 spec 四件套到收口报告的契约流水线：契约先于实现落盘、每个契约都带状态机、每层之间都有双向追溯，还专门建了一道「反向推导」的 FPF 审查来抓正向链自造的矛盾。** 最强的是分层 + 反向推导；相对最弱的是「结构化」——大部分契约是 Markdown 而非机械可解析，只有 env 契约真正可执行。

## 框架回顾（SDD 四维）

| 维度 | 问的问题 | 判断 |
|---|---|---|
| **结构化** | 契约可机械解析吗？字段/状态/边界是否固定 | 🟡 半结构化——文档层强，机器层弱 |
| **显性化** | 契约是否落盘、可执行、非对话记忆 | 🟢 强——磁盘真相源 + 可执行门禁 |

| **反向推导** | 是否从契约反推实现/反查矛盾 | 🟢 强——FPF 是专门的反向验证通道 |

## 1. 结构化：半结构化——文档层强，机器层弱

### 已确认优点
- **spec 四件套有固定结构**（`01-requirements` / `02-design` / `03-tasks` / `04-fpf-review`），每件内部节固定：
  - `01`：Introduction / Glossary / Requirements（EARS）/ AC / 依赖 / Owner 批复台账
  - `02`：硬约束遵循 / Architecture / Components / Correctness Properties / Error Handling / Testing
  - `03`：Task Groups（Group 0 前提复核 → 实施组）/ 追溯矩阵 / 收口记录
  - `04`：FPF D1-D5 五维 / Q4 独立发现
- **INT-001 契约自带契约元数据**：版本号、创建日期、实施对照 HEAD、供给方/消费方、权威事实源引用（`ccaf101-facts.ts`）、「双方签收段」——是一个规范结构的接缝契约
- **00-INDEX 是结构化枢纽**：项目约束清单（权威单点）/ 决策台账 / Owner 批复 / 热点表 / 波次计划 / 矩阵概览 / 覆盖审计 / 收口表
- **状态词是固定拼写的枚举**：`状态判定` 五态 + 需求状态词汇（Draft→Ready-for-Specs→…→Closed，旁路 Frozen/Blocked）

### 确认问题
**P2 — 结构化停在「文档约定」，未到「机器校验」**
- 除 env 契约（`env-contract-check.ts`，281 行 AST 级提取 + 三方对账）是真正机械可执行的，其余契约（spec 四件套、INT-001、00-INDEX）都是 **Markdown**，字段名靠人工拼写对齐，无 schema 校验
- 后果：字段名一旦拼错（历史出现过「最终状态」vs 磁盘既有「状态判定」臆造），机械守门就退化——loop 空转、守门永假。这正是 loop-prompt-generator 里反复强调「字段名先 grep 对齐磁盘」的原因

**P2 — INT-001 是「草案，待双方签收」却已落后代码**
- 契约头标版本 0.1、状态「待签收」，但（三层地图审计已证）`PRICE_ENTITLEMENT_MAP` 代码里已有 4 个映射、`revokeEntitlementsByInvoice` 已存在且支付退款路径已调用——契约正文仍写「部署期为空、退款需未来抽取」
- 结论：**门牌存在但写的是旧房间用途**；结构化能保证「契约在」，不能保证「契约新」

## 2. 显性化：强——磁盘真相源 + 可执行门禁

### 已确认优点
- **契约落盘，非对话记忆**：00-INDEX 是队列真相源、03-tasks 收口记录是完成证据、GOAL 完成判定 = 磁盘事实（收口记录状态判定 + 验证证据 + 00-INDEX 行 + 报告存在四条件）
- **环境契约三重可执行**：`required-env.ts`（代码契约）→ `env-contract-check.ts`（校验脚本，AST 提取 + 对账）→ CI `check:env`（机械门禁）。这是全仓最成熟的「契约显性化」
- **`guard:attribution-secret`** 也是脚本门禁（扫脚本里未加门的 secret 自默认值）
- **收口记录即证据**：「无收口记录 = 未收口」——完成的唯一证据是写进文件的记录，不是对话宣布
- **Owner 批复显性化**：00-INDEX 有 Owner 批复清单，Task 5.1 从可选升默认范围都有批复出处留痕（2026-07-27）

### 确认问题
**P2 — 显性化依赖文档纪律，缺机械断言**
- 「收口表 Σ 状态判定 = 00-INDEX 实施表」无脚本校验，靠人维护对齐
- 「无收口记录 = 未收口」是纪律，不是门禁（与拆卡审计同一条）

## 3. 分层：强——10 层矩阵 + 00-INDEX 枢纽 + 下游 specs

### 已确认优点
- **10 层技术分类法**：`00-INDEX`（导航枢纽）/ `10-BL` / `20-API` / `30-DB` / `40-UI` / `50-INT` / `60-SEC` / `70-CODE` / `80-OBS` / `90-TEST` / `99-DEP`，每层前缀固定（BL-501 / UI-901 / OPS-901 …）
- **00-INDEX 是唯一入口**：项目约束清单（权威单点）、决策台账、Owner 批复、热点表、波次计划、覆盖审计、收口表全在这里聚合——AI 从这一份文件能判断整个专项状态
- **空层不填充理由**：00-INDEX 明确记录哪层为何不填（结构诚实，不假装完整）
- **三层结构完整**：需求矩阵（requirements/）→ spec 四件套（requirements-specs/NN-layer/）→ 实施收口
- **跨切面实施告警**：00-INDEX 有热点表 + 跨切面告警，防止多 spec 并行改同一文件

### 确认问题
**P2 — 分层只在专项内，仓库级缺父级索引**
- 各专项的 00-INDEX 互不相连，`站点优化-ongoing/` 无父级总索引（三层地图审计已证）
- 单层强，跨层导航靠 AI 猜

## 4. 反向推导：强——FPF 是专门的反向验证通道

### 已确认优点
- **正向链是推导生成的**：
  - `requirements-matrix-generator`：差距分析/审计报告 → 10 层分类 → 00-INDEX + N 需求文档 → 场景覆盖度审计（含 finding ID 去向追溯表，21 行逐条可核）
  - `spec-dev`：7 阶段 Discovery → Requirements → Design → Tasks → FPF → Implementation → Verification，从需求矩阵批量生成 spec 四件套
- **FPF 是反向验证**：`04-fpf-review.md` 不是正向重复，而是**读 02/03 反查 01 的矛盾**——D3 追溯矩阵完整性（检查矩阵 Task 列 ↔ Task 自身 Validates 一致性）、D5 可测试性（检查 Property oracle 可证伪性）、Q4 独立发现（作者自陈之外）
- **反向推导抓到正向链自造的 bug（实证）**：FPF 独立发现 F-1（`--debugview` 幽灵能力——三处依赖零实现）、F-2（Req 3.4 参数键校验结构上不可证伪）、F-3（Property 9 与 Task 5.1 自我矛盾）。**这正是「作者 ≠ 审查者」的反向机制在起作用**——正向生成再严密，也会自造 latent 矛盾，只有反向通道能抓
- **R_eff 机械规则**：R_eff = min(D1..D5)，禁止手工上调/下调；≥0.95 直接实施 / 0.80-0.89 不可实施 / <0.80 重新设计
- **追溯矩阵双向**：01 AC ↔ 02 Property ↔ 03 Task Validates，双向全覆盖无空白

### 确认问题
**P1 — 反向推导是「人审流程」，不是机械门禁**
- FPF 的 F-1/F-2/F-3 是审查 agent 逐条 Read 抓出来的，依赖审查者的认真与覆盖，不是脚本保证的
- R_eff 机械规则存在，但评分本身靠审查者判断（04 里 F-6/F-7 是对作者自陈项的「定性升级」——作者低估严重度），不是自动计算的分数
- 后果：反向通道强，但**强在流程纪律，不在自动化**；审查者漏读一处，矛盾就静默通过

## 现状判断（SDD 四维）

```text
结构化     🟡  文档结构强，机器校验弱（仅 env 契约可执行）
显性化     🟢  磁盘真相源 + 可执行门禁 + 收口即证据
分层       🟢  10 层矩阵 + 00-INDEX 枢纽 + 空层诚实
反向推导   🟢  流程强（FPF 抓正向自造矛盾），但靠人审非自动
```

**梯度结论**：项目的 SDD 是「文档驱动的规范开发」而非「机器强制的契约开发」。它用**分层矩阵 + FPF 反向人审**替代了「契约自动生成 + 契约自动校验」——在 AI 长跑场景下这已足够强（OPS-901 12 任务全收口 PASS），但机械层（env 契约）与文档层（spec/接缝契约）的成熟度差了两个量级。

## 确认问题汇总（P 级）

| 级别 | 维度 | 问题 |
|---|---|---|
| P1 | 反向推导 | **FPF 靠人审非自动**：F-1/F-2/F-3 靠审查 agent 逐条 Read 抓到，R_eff 评分靠审查者判断，无自动校验。审查漏读一处即静默通过 |
| P2 | 结构化 | **契约是 Markdown 非机器可解析**：仅 env 契约 AST 级可执行，其余 spec/接缝契约无 schema 校验，字段名靠人工拼写对齐 |
| P2 | 结构化 | **INT-001 是「草案待签收」却已落后代码**：PRICE_ENTITLEMENT_MAP 已有 4 映射、revokeEntitlementsByInvoice 已存在，契约正文仍写旧态 |
| P2 | 显性化 | **收口对齐靠纪律非门禁**：收口表 Σ 状态判定 = 00-INDEX 实施表无脚本断言 |
| P2 | 分层 | **分层只在专项内**：00-INDEX 互不相连，仓库级缺父级索引 |

## 与三层地图 / 拆卡审计的关联

- 三层地图审计看「地图层」（导航在退步）；拆卡审计看「执行控制面」（拆卡/守门/续跑已成熟）；本份 SDD 审计看「契约层」（分层 + 反向推导是强项）。
- 三条合起来，项目的真实画像：**执行面（拆卡）和契约面（分层/反向）都很强，弱的是地图层（导航）和机械层（契约机器可解析度）**。契约强在「人有纪律地写」，弱在「机器没强制读」。

## 建议下一步（最小可用，先设计后落盘）

1. **把 env 契约的「可执行」模式复刻到最热的接缝契约**——INT-001 的 `PRICE_ENTITLEMENT_MAP` 语义已落后代码，值得像 env-contract-check 一样加一个 AST 级对账脚本（提取代码真实 map ↔ 契约声明 map），把「门牌写旧用途」变成「门牌过期即报错」
2. **给 spec 四件套加 schema 校验**——字段名（状态判定五态、AC 编号、追溯矩阵行数）用脚本断言，把「字段名对齐磁盘」从纪律变成门禁（对齐 env-contract-check 先例）
3. **收口表 ↔ 00-INDEX 实施表加 Σ 机械断言**——「无收口记录 = 未收口」从纪律变门禁
4. **（可选）FPF 结论机读化**——F-1~F-7 目前是叙述，若抽成结构化字段（severity / 影响文档 / 状态），可被收口门禁引用
