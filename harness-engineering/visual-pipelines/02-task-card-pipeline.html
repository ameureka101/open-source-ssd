目标信封：GOAL

信封 · 评估模型守门

一个极薄的「信封」，只装 /goal 指针 + 停止条件 + 红线摘要 + 上限阀。因 /goal 有 4000 字符硬上限，九块全文落盘到契约文件，这里只留让评估模型能机械判定的东西。

站点优化-ongoing/06-24 小时干geo-seo/GOAL-wave1-ops901-2026-07-28.md

信封里有什么

  • 指针 — 契约文件绝对路径
  • 上限阀 — stop after 80 turns
  • 续跑指令 — 上限命中重发本 goal，从磁盘续跑

完成判定（磁盘事实）

  • (i) 收口记录 状态判定 = PASS / 已修复
  • (ii) Step 6.0 · 验证证据 · 对抗验证 实测
  • (iii) 00-INDEX 该 spec 行已更新
  • (iv) EXECUTION-REPORT 已存在
红线回显。 违反即不可逆的动作（push / 部署 / 生产写 / gh workflow run / flag 翻转 / 切分支）直接写进 /goal 常驻，否则 compact 后会被丢掉。生产动作必须写成精确请求并等待 Owner，不得伪装成 deferred。

第 3 站

任务卡：03-tasks.md

拆卡落点 · 4 件套之一

大任务真正被「拆开」的地方。每个 spec 包四件套（01-requirements / 02-design / 03-tasks / 04-fpf-review），任务卡把 spec 拆成可分组的实施单元，每张卡带验收标准与依赖。

requirements-specs/80-observability/OPS-901-…/03-tasks.md

任务卡字段

  • Description — 做什么
  • Files to modify — 改哪些文件
  • Acceptance Criteria — 怎么算过
  • Validates / Dependencies — 追溯与先后
  • Effort — S/M 工时估算
  • Status — 当前态

OPS-901 任务分组

  • G0 前提复核 — Step 6.0 重验 19 锚点
  • G1 验证脚本 · G2 守卫升级
  • G3 CI 守卫 · G4 执行证据与回归门
  • G5 Owner 侧（Task 5.1 默认交付）
  • 12 任务 · 33 行双向追溯矩阵 · ~20–40h

收口记录 尾部 ## 收口记录 的 状态判定 五态词汇（PASS / PARTIAL / FAIL / spec-premise-stale / deferred-non-blocking）是 /goal 机械守门的字段。铁律：无收口记录 = 未收口。

收口报告：EXECUTION-REPORT

红线层 · 精确 Owner 请求

整条链路的终点。生产验证永远不放进行自主范围——即使代码本地 PASS，部署 / 发哨兵 / workflow dispatch 都写成「待 Owner 单独批准」，并附副作用、证据、回滚，绝不伪装成 deferred。

站点优化-ongoing/06-24 小时干geo-seo/EXECUTION-REPORT-wave1-ops901-2026-07-28.md

报告结构

  • Scope / Step 6.0 复核
  • 逐任务结果表
  • 质量证据表（命令 + exit code）
  • 对抗验证

两条收口保证

  • Exact Owner Production Request — 4 项精确请求
  • Red-Line Self-Audit — 逐条声明未触红线

这条流水线成熟在哪

四层全部用真实文件跑通：GOAL 信封只有 06 用足，契约 + 任务卡 + 报告三层则全专项共用（013 已逐波一份契约）。差距不在机制，而在 GOAL 信封没沉淀成模板，轻量专项仍靠文档目录自然分层。

守门是机械的 —— 停止条件字段名对齐磁盘，评估模型能判定；上限命中 ≠ 失败，重发同一 goal 从磁盘续跑。生产动作永远不进波次自主范围。

GOAL 信封仅 06 用足 契约/任务卡/报告全专项共用 锚点重读表用行号，会漂移 进度双写，靠纪律对齐
