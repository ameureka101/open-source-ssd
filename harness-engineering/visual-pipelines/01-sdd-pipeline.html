  • OPS · QA · DEP — 运维/测试/部署

spec 四件套

显性化 · 契约先于实现落盘

每条需求经 spec-dev 生成四件套，契约先于实现写进磁盘。01 定义「要什么」，02 定义「怎么设计」，03 拆成「任务卡」，04 做「反向证伪」。这是整个 SDD 的心脏。

spec-dev → requirements-specs/…/OPS-901-…/{01,02,03,04}*.md

01 → 02 → 03 正向链

  • 01 requirements — EARS 需求 + AC + 依赖
  • 02 design — 硬约束 + Properties + 接口
  • 03 tasks — 任务卡 + 追溯矩阵 + 收口记录

可执行契约（最强样本）

  • env 契约三重 — required-env → check 脚本 → CI
  • guard:attribution-secret — 脚本门禁
  • 收口即证据 — 无收口记录 = 未收口

FPF 反向证伪

反向推导 · 作者 ≠ 审查者

04-fpf-review 不是正向重复，而是读 02/03 反查 01 的矛盾。作者自陈薄弱处之外，独立发现 F-1~F-7（幽灵能力、恒真断言、自造矛盾）。这是抓「正向链自造 latent 矛盾」的唯一通道。

04-fpf-review.md · D1-D5 五维 + Q4 独立发现

D1-D5 五维

  • D1 需求完整性 · D2 设计覆盖率
  • D3 任务追溯性 · D4 术语一致
  • D5 可测试性（oracle 可证伪）

R_eff 机械规则

  • R_eff = min(D1..D5)，禁手工上调
  • ≥0.95 直接实施 · 0.80-0.89 不可实施
  • <0.80 重新设计

反向证伪闭环（实证）

FPF 在 OPS-901 独立抓到 F-1（--debugview 幽灵能力：三处依赖、零设计零实现）、F-2（Req 3.4 参数键校验结构上不可证伪）、F-3（Property 9 与 Task 5.1 自我矛盾）。正向生成再严密，也会自造矛盾——只有反向通道能抓。

这条 SDD 流水线强在哪

项目是文档驱动的规范开发而非机器强制的契约开发。它用 分层矩阵 + FPF 反向人审 替代了「契约自动生成 + 契约自动校验」——在 AI 长跑场景下已足够强（OPS-901 12 任务全收口 PASS）。

分层与反向推导是强项；相对弱的是结构化——大部分契约是 Markdown 非机器可解析，只有 env 契约真正可执行。机械层与文档层的成熟度差了两个量级。
