## 内容与事实奠基（Content & Fact Foundation）

> 本阶段是整条 pipeline 的真理地基。所有下游（设计 tokens、Stitch 出图、Next.js 实现、i18n 字典、SEO）都从这一层派生。**改任何业务文案，必须先回到这一层改源，再单向传导**——这是 pixel-labs 在 `content/README.md` 末尾「协作方式」与 KT-002 中反复写死的铁律。
>
> 受 **{{PROJECT}} AGENTS.md §2** 约束：本阶段产出的所有文案/案例/合规声明，(1) 不得仿造或暗示 the AI provider 的官方视觉与品牌；(2) 任何 KPI、客户案例、Partner 身份、认证状态在发布前必须经人审；(3) 敏感事实未经授权一律标记「待确认」，不得直接进入成品稿。

---

### ① 目标

把分散的业务真相采集、核实，并**结构化为一个分模块、可溯源、带元数据头的「内容真理层」**，使其同时满足三种下游消费者：内部对齐（规划稿）、生成式出图（Stitch prompt 的内容溯源）、最终实现（i18n 字典）。本阶段结束时应达成：

1. 锁定 **6 坐标元数据头**（项目类型 / 目标 / 受众 / 技术栈 / 设计体系 / 品牌），作为后续一切内容与设计不得偏离的对齐基准（对应 `content/README.md` 顶部引用块）。
2. 把官网拆成 **有序编号的内容板块**（pixel-labs 实例为 `content/01_company_about` ~ `09_team_authority`），编号顺序即访客信任建立动线（我是谁→卖什么→能做什么→怎么联系→凭什么信），每板块一个目录 + `README.md` + 一句 `> 模块目标` 声明「要让客户相信什么」。
3. 建立 **单向真理传导链**：`content/01-09`（业务源）→ `content/design/pages/*`（设计稿）→ `content/design/stitch_prompts/*`（出图 prompt）→ 落地层（mk-saas 的 `messages/*.json` 或 `content/*.mdx`）。
4. 区分 **规划稿 vs 成品稿**：内部对齐用的规划稿（可中文、含「待讨论问题/视觉建议」）与可直接上线的成品文案（目标语言 + 目标品牌嗓音）物理分离。
5. **核实业务真理**：把敏感 KPI、客户案例、创始人/团队身份、Partner/认证状态做事实分级，未经证据/授权的一律标记「待确认」。

### ② 输入

- 散落的业务事实来源：创始人访谈、产品功能清单、定价梯度、真实/典型客户案例、团队履历、合规与部署能力。
- 品牌内核草案：公司真名 + 可选 IP 形象 + 一个带立场的设计哲学专名（pixel-labs 实例：PIXEL PENGUIN LABS / 智眼企鹅 / Anti-Slop Brutalist SaaS）。
- 受众与商业目标定义（pixel-labs 实例：2B、年收入 $10M+、品牌展示 + 获客转化）。
- 若为既有站迁移：现有 mk-saas 模板的占位内容（`content/` MDX 与 `messages/*.json`），用于差异盘点（**这一步同时要证伪「本站基于什么模板」的假设——pixel-penguin-web 实际并未采用 mksaas，靠 `grep mksaas/better-auth/drizzle` 0 命中证实**）。

### ④ 用什么 skill + 工具 + 命令

- **Skill**：
  - `website-content-discovery`（项目内 `_skills/website-content-discovery.md`，`content/README.md` 操作指南表指向）：从零梳理内容。
  - `knowledge-validator` / `knowledge-distiller`：把散落事实结构化、建立 SSOT、剔除幽灵实体（documented but non-existent）。
  - `competitor-analyzer` / `business-model-designer`：补全定价梯度与商业模式表所需的事实。
  - `brand-strategy-design`：确立品牌三件套与嗓音（产出物喂给「待讨论问题」而非直接定稿）。
- **工具 / 命令**（事实核实与污染审计，全部用绝对路径运行）：
  - 文案污染负向断言（KT-025 现场已存在：案例文件里 `the AI 3 Opus`、`the AI Development` 等是全局 find-replace 误伤的证据）：
    `grep -rn "the AI 3\|A the AI\|the AI Applications\|the AI Development" {{CONTENT_DIR}}` 应清洗后归零（保留 `the AI industry/provider` 这类合法冠词+名词）。
  - 占位/待确认扫描：`rg -n 'TODO|TBD|待确认|待讨论|未定|示例' {{CONTENT_DIR}}` —— 成品稿区不应命中。
  - 身份一致性核对（已知不一致：`content/README.md` 写创始人 Ethan Chang，对外公开身份为 Yichuan Zhang）：`grep -rn "Ethan Chang\|Yichuan" {{CONTENT_DIR}}` 须刻意统一。
  - 板块骨架完整性：`find {{CONTENT_DIR}} -name README.md | sort`。

### ⑤ mk-saas 落地映射（本阶段产物对应改哪些文件）

> 关键解耦点：pixel-labs 的 `content/01-09` 是**业务真理源**，与 mk-saas 的**渲染源**是两层。本阶段只产出/核实真理源；真正灌入 mk-saas 是下游阶段的事，但本阶段必须**预先规划好映射目标**，否则会落入 KT-002（改单 surface 不改源链）。

| 本阶段真理源 | mk-saas 落地目标 | 说明 |
|---|---|---|
| 6 坐标元数据头 + 站点级事实（站名/域名/受众） | `src/config/website.tsx` | mk-saas 站点配置（名称、URL、metadata 基址）。属集中化单一源，对应 KT-008 禁止页面内联 meta。 |
| 板块成品文案（营销页文字） | `messages/en.json` / `messages/zh.json`（mk-saas 用 next-intl 的 JSON 命名空间） | **全 UI 文案唯一真理**。en 为结构源，其余 locale 必须 key 树对齐（缺键即编译/运行期暴露）。pixel-penguin-web 的对应物是 `src/i18n/dictionaries.ts`。 |
| 案例 / 长文 / 博客式内容 | mk-saas `content/`（author/blog/category/pages 的 `.mdx`） | mk-saas 用 Fumadocs MDX 承载长内容；案例四段式可作为 page/blog MDX。i18n 走文件名分割（`*.mdx` / `*.zh.mdx`）。 |
| 品牌资产（Logo/OG/favicon） | `public/`（logo.png / og.png / favicon.* 等） | **只引用不内嵌**。源资产留在 `_docs/.../ASSETS_VAULT/` 但严禁进版本库（见 KT-007）。 |
| 页面级文案的承载组件 | `src/`（页面/section 组件，仅消费上面三处，不硬编码文案） | 组件从 `messages`/`website.tsx`/MDX 取数，禁止把英文写死在组件里。 |

> 注意：mksaas-template 自带 `better-auth/drizzle/fumadocs` 全套后台能力，本阶段**不触碰**——内容奠基只关心 `website.tsx` + `messages/*.json` + `content/*.mdx` + `public/` 四个落地面。

### ⑥ 人审门控（{{PROJECT}} §2 强制）

进入下一阶段（设计/出图）前，必须由 Owner 逐项确认并签字：

1. **敏感 KPI 门控**：所有量化成果（如「成本降低 X%」「follow-up +55%」）须有公开/NDA 后证据；无证据者改为方向值或标 `metrics under NDA`，不得给绝对值。
2. **案例真实性门控**：每个客户案例的「行业契合 + 客户画像」经 Owner 确认为真实或明确标注为「典型场景」；未确认不得进入成品稿（对应 AGENTS.md「未经 Owner 确认不实现案例页」）。
3. **身份门控**：创始人/团队对外公开身份统一核定（Ethan Chang vs Yichuan Zhang 必须二选一并全局一致）。
4. **合规边界门控**：不得在任何成品稿出现 **Partner 身份既成声明**（官方批准前）、未获批的 **SOC2/HIPAA/认证** 既成事实、固定 SLA 数字（除非有部署级证据）；信任中心一律用 readiness roadmap 措辞。
5. **品牌视觉合规**：成品文案与品牌叙事不得仿造或暗示 the AI provider 官方视觉/身份（§2）。

门控产物：上述「事实核实清单」中所有「待确认」项清零或显式 waive，方可放行。

### ⑦ 本阶段相关的 known-traps

- **KT-002 改单一 surface 不改源链**：本阶段确立的传导链就是为防它而生——内容是业务真理，但落地真理在 `messages/*.json`（mk-saas）/`dictionaries.ts`；只改下游不回改 `content/01-09` 会造成各层漂移。
- **KT-025 英文文案退回通用企业腔 / find-replace 污染**：案例文件现存 `the AI 3 Opus`、`the AI Development` 等全局替换误伤痕迹，是 P0 级污染，出图前必须先清洗内容源；同时用「若这句能出现在任何咨询公司官网就重写」作为嗓音硬闸。
- **KT-007 暴露 ASSETS_VAULT**：内容奠基会触及品牌/法人资料；护照/EIN/银行号所在的 `ASSETS_VAULT/` 严禁被引用或入库，品牌资产改用 `_docs/03-资产交付/` 或 `public/`。
- **KT-009 案例数据硬编码**：案例必须集中在内容源/字典单点维护，禁止把 KPI、叙事直接写进页面组件（防 listing 与 detail 跨 locale 错位）。
- **规划稿当成品发（KT-002 的具体形态）**：`01-04` 多为含「待讨论问题/示例数字」的中文规划稿，这些占位/示例 KPI 不得直接上线，必须经 Owner 确认或替换为可证据化指标。
- **身份/Partner 过早公开（关联 KT-028）**：对外文档实体命名需刻意对齐；Partner 身份在官方审批前不得出现在任何公开面。
