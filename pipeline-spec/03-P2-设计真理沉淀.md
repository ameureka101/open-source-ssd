## 设计真理沉淀(Design Truth: tokens→components→pages)

> 阶段定位：P2 是把 P1 的品牌方向"压成可执行的真理三层"——变量(色/字/间距/动效/质感)在最底层定义一次，组件规范向上引用变量、页面 wireframe 向上引用组件。上层只允许向下传导、不允许反向硬编码；各层职责单一，任何一处视觉细节都能沿"页面→组件→token"逆向追到唯一源头。
>
> {{PROJECT}} 当前状态（2026-06-07）：本文件仍保留 pixel-labs 方法论表述；执行 {{PROJECT}} 站点时，视觉真理以 `content/design/output/unified_blueprints/` 和 P5.1 回写后的 FG 体系为准。若正文示例出现 `#EA580C`、Instrument Serif、`ppl-*` 等旧项目值，只当示例，不覆盖当前 {{PROJECT}} 的 `#222222` / `#F0EFEA` / `#D4930D` / `#E7B04A` 视觉事实。

### ① 目标

沉淀一套**单一事实源(SSOT)的三层设计真理**，并保证它逐层向下传导：

1. **变量真理层(tokens)**——把色彩、字体、间距、动效、质感(噪点层)、圆角/边框/阴影策略全部收敛成命名变量，定义一次、全站引用。这是 pixel-labs 的 `content/design/design-tokens.md`(色 `#F0EFEA`/`#222222`/`#EA580C`、字 Instrument Serif + Geist + JetBrains Mono、间距 `py-24`/`py-32`、动效"仅 150ms color shift"、质感"全局唯一 noise overlay")。
2. **组件规范层(components)**——所有页面共享的导航/按钮/表单/Bento/定价/排版组件,**每条规则只引用变量,不写死数值**(pixel-labs `components.md`)。
3. **页面真理层(pages)**——逐页 ASCII wireframe + 元素级标注(每个元素标明用哪个字体 token、哪个色 token、哪个间距)+ 深浅节奏序列(Home: Light→Light→Light→Dark→Light)。

判定标准:页面里任何一个色值/字号/间距,都能逆向追到组件规范、再追到 token,**不存在孤立的一次性 hex 或魔法数字**。

### ② 输入(从 P1 品牌方向 + 内容层拿到什么)

| 来源 | 拿到的东西 | 在本阶段的作用 |
|---|---|---|
| P1 品牌方向 | 设计哲学(pixel-labs 的 "Anti-Slop Brutalist SaaS / Typography does the heavy lifting")、品牌语气、Logo 规范、配色基调、字体家族选择 | 决定 token 的取值与"禁止清单"(无渐变/无阴影/无圆角>2px/无 emoji) |
| 内容层(content/01-09) | 每个模块的真实文案、指标、定价、信任信号、案例数据 | 决定 wireframe 里每个 Section 装什么内容,文字长度反过来约束排版 token |
| P1 的 traceability 约定 | "content source → design → output → implementation" 的链条 | 本阶段产物必须标注内容来源(pixel-labs `00-global-system.txt` 底部的 Content Sources 映射表) |

关键纪律(对应 KT-002):**先有内容源,再做设计真理**。不能先画一个漂亮 wireframe 再去凑文案,否则实现层会同时偏离业务真理和设计真理。

### ③ 输出交付物(门控产物)

四份可作为门控(gate)的产物,缺一不可:

1. **`design-tokens.md`**——变量真理。分区:Colors / Typography / Spacing / Layout / Border&Radius / Shadows(本系统明确写"无") / Effects(噪点层) / Motion Rules(允许 vs 禁止两张表)/ Logo 规范。每个 token 三列:`Token | Value | Usage`。
2. **`components.md`**——组件规范。导航(桌面+移动)、按钮(Primary/Ghost/Submit + 禁止样式)、表单(仅底边线、placeholder 即 label)、Section 布局(Light/Dark + 深浅交替节奏表)、排版组件(Giant Text/Numbered List/Process Steps/Trust Badge)、Bento Grid、定价表(代码清单式、非卡片)、Footer、响应式规则。
3. **`pages/*.md`**(逐页)——每页含:页面目标/用户行为/URL、布局底座说明、逐 Section 的 **ASCII wireframe** + 元素级标注(主标题用什么字体 token+字号+色、副标题、CTA 用哪种按钮)+ 该页**深浅节奏序列**。
4. **`stitch_prompts/`**——自包含的生成提示词:`00-global-system.txt`(跨页一致性校验基准,不是 prompt 本身)+ `01~06` 各页独立 prompt。`00` 文件是三层真理的"压缩快照",底部带 Consistency Checklist。

门控含义:这四份产物未齐、或彼此对不上(如 token 改了但 components 没跟),**P2 不算通过,不得进 P3 落地**。

### ④ 用什么 skill + 工具 + 命令

- **Skill**:`brand-strategy-design`(承接 P1 视觉识别,定 token 取值)、`detailed-design-guide`(前端组件/页面结构设计)、`specs-writer`(把组件规范写成可验收条目)、`webapp-testing`(P3 落地后逐页视觉 QA、截图比对节奏与一致性)。
- **生成工具**:Google **Stitch** 出页面草图——但严格按 pixel-labs README 的"方式 B(精确布局)":上传 `pages/xxx.md` 作附件 + 粘贴对应 `stitch_prompts/0X-xxx.txt`。Stitch 产物**只当 blueprint**(见 ⑦ KT-001)。
- **校验命令**(pixel-labs 真实做法):
  - `./scripts/anti-slop-audit.sh` —— 扫描渐变/阴影/圆角>2px/黑底/一次性 hex 等违规。
  - `rg -nE "rounded-(md|lg|xl|full)|shadow-|#000000|linear-gradient" src` —— token 漂移自查。
  - 对照 `stitch_prompts/00-global-system.txt` 底部 Checklist 逐项过(噪点层、字体、CTA 色、深色用 `#222222`、导航/页脚跨页一致、Logo 一致)。

### ⑤ mk-saas 落地映射(基于 mksaas-template 真实结构)

实测 `mksaas-template-main` 是 **Tailwind v4 + `@theme inline` 的 CSS 变量体系**,三层真理的落点非常清晰(路径基于 `_opensource/mksaas-template-main/`):

| 本阶段产物 | 落到 mk-saas 哪里 | 怎么改 |
|---|---|---|
| **tokens(色/圆角/阴影)** | `src/styles/globals.css` 的 `@theme inline { … }` 块 + `:root` / `.dark` 变量 | 把模板默认的 `--primary/--background/--radius/--shadow-*` 等改写成 PPL 取值:`--background:#F0EFEA`、暗色 section 用 `#222222`、`--primary:#EA580C`;关键是把 `--radius` 压到 0(模板默认有 `--radius-sm/md/lg/xl` 派生,圆角>2px 必须清零)、并移除/置空 `--shadow-*`(本系统"无阴影")。建议新增一组 `--ppl-*` 命名变量承载噪点 opacity、py-24/py-32 间距,避免污染模板语义 token。 |
| **字体 token** | `src/styles/globals.css` 的 `--font-*` + Next.js `next/font` 注册(`src/app` 字体引入)+ `website.tsx` 无字体项则在 layout 注入 | Instrument Serif(heading)/ Geist(body)/ JetBrains Mono(mono),禁用 Inter 作 body。CJK 注意见 ⑦ KT-016。 |
| **主题开关** | `src/config/website.tsx` 的 `ui.theme.defaultTheme` | 设定默认主题、是否暴露深浅切换(本设计靠 Section 级深浅节奏,而非全站 dark mode,需评估是否锁定 `defaultTheme`)。 |
| **组件规范** | `src/components/{ui,blocks,layout,page,custom}` | `ui/` 是 shadcn 基元(button/input 等)——按 `components.md` 重写其 variant(Primary/Ghost/Submit、表单仅底边线);`layout/` 改 Navbar/Footer 成跨页一致的单一 shell;`blocks/`、`page/` 承载 Hero/Bento/定价清单等页面级组件。**禁止保留 shadcn 默认圆角/阴影**。 |
| **逐页 wireframe** | `src/app/[locale]/(marketing 路由)/**/page.tsx` | 按 `pages/*.md` 的 Section 顺序与深浅节奏拼装组件;页面内容来自字典/内容源,不在组件里硬编码文案。 |

> 注意:模板自带 `magicui`/`animate-ui`/`tailark` 等带动效/装饰的组件目录——这些大多违反"禁止 scale/translateY/入场动画",落地时**默认不启用**,要用先按 Motion Rules 裁剪。

### ⑥ 人审门控(受 {{PROJECT}} `AGENTS.md` §2)

- **§2 约束 4 + 全局红线·禁仿视觉**:本阶段产出的 token/组件/页面,**不得在视觉上模仿、致敬或暗示 the AI provider 官方视觉识别**(配色、品牌字、Logo 形态、官方页面版式)。设计真理走的是独立的 PPL/{{PROJECT}} 品牌语言,生成出来若出现"像官方"的观感,门控直接驳回。
- **§2 约束 5 · 发布前人审(发布=不可逆)**:P2 产物属于"草稿/待发布队列",**任何对外可见的视觉(站点上线、对客户的设计稿、社群展示)发出前必须经人类伙伴审阅批准**。Agent 可起草 token、画 wireframe、跑 Stitch,但**不得自行点发**;一处批准不等于处处批准,换页面/换渠道要重新确认。
- **§2 约束 3 · 双品牌一致性**:C 端落点({{PRODUCTION_DOMAIN}})与 B 端({{PARENT_DOMAIN}})的视觉定位/价格段不得在 token 或文案里混用;对外署名统一 `{{BRAND_PARTNER_SIGNATURE}}`。
- 审阅清单建议直接复用 `00-global-system.txt` 底部 Consistency Checklist + anti-slop 审计结果作为人审的客观依据,人类只需在其上做"品牌合规 + 禁仿"的主观判断。

### ⑦ 本阶段相关的 known-traps(摘自 pixel-labs `.harness/known-traps.md`)

- **KT-001 · 把 Stitch 产物当生产代码**:Stitch 导出的 `code.html` 含 CDN Tailwind、内联 config、MD3 token、Material Symbols 和页面局部 Navbar/Footer。**正确做法**:Stitch 只当蓝图,提取结构/视觉节奏/文案,重写成使用本地 `ppl-*`(落地后即 mk-saas 的 `@theme` 变量)的 typed Next.js 组件。**验证**:源码里不应出现 CDN Tailwind、Material Symbols、MD3 token 名。
- **KT-004 · 视觉修复后的 token 漂移**:用临时 hex 或 Tailwind 默认值修单个视觉问题,会悄悄把渐变、阴影、默认圆角、纯黑底、一次性颜色带回来。**正确做法**:只用 `globals.css` 里的命名 token 和既有组件模式。**验证**:跑 `./scripts/anti-slop-audit.sh` 再看受影响路由截图。这是"上层向下传导"原则最容易被破坏的点——一旦页面层出现 token 之外的硬编码,三层真理就断链。
- **KT-002 · 改一处不连带改它的来源链**:在实现层改文案/视觉却不回看 `content/01-09` 和 `content/design/`,会让实现同时偏离业务真理和设计真理。**正确做法**:从内容源出发 → 改设计生成面(tokens/components/pages/stitch_prompts)→ 再改实现。**验证**:impact map 列全 source/design/output/implementation/verification 五个面。
- **KT-016 · CJK 字体与排版漂移**:对中文/日文/韩文滥用 `uppercase`、超宽 `letter-spacing`(tracking-widest)、`font-mono` 标签——CJK 字符无法被有意义地大写或拉宽。**正确做法**:落地后用 `src/i18n/style.ts` 的 `labelClass()/compactLabelClass()/displayClass()` 做 locale 自适应排版,手动覆盖前先 `isCjkLocale()` 判断;`globals.css` 加 CJK 覆盖。对 {{PROJECT}}(中文为默认语言)这条尤其关键——很多 Anti-Slop 大写/mono 标签的英文设计真理,**必须在 token/组件层就预留 CJK 分支**,不能等到页面层硬塞。
- **KT-003 · 全局壳层漂移**(导航/页脚):shell 改动只在当前路由验证。**正确做法**:壳层改完至少在 `/`、`/about`、`/cases`、`/contact` 浏览器核对,确认每页只有一个 header、一个 footer——这正是"组件规范层职责单一、跨页一致"的落地校验。

> 一句话收束本阶段:**变量定义一次、组件只引用变量、页面只引用组件**;Stitch 是草图不是真理,token 是真理不是建议;一切视觉细节可沿页面→组件→token 逆向追溯到唯一源头,且发布前过人审。
